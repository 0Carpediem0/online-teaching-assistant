# Подготовка backend к развёртыванию

Инструкция поднимает API проекта на Linux-сервере через Docker Compose. По умолчанию API использует облачную модель DeepSeek Flash; для этого серверу нужен исходящий HTTPS-доступ в интернет. Локальная Ollama включается отдельно профилем Compose. API опубликован на loopback сервера (`127.0.0.1:8787`); для доступа из сети организации перед ним нужен HTTPS reverse proxy (например, nginx). Прямой доступ к API из интернета не предусмотрен.

## Что уточнить у организации до установки

- имя или IP внутреннего сервера, доступ по SSH и ответственного администратора;
- Linux-дистрибутив, Docker/Compose, доступность NVIDIA GPU и настройку NVIDIA Container Toolkit, если нужен GPU;
- DNS-имя для API, сертификат TLS и сетевое правило от клиентских компьютеров до HTTPS reverse proxy;
- разрешённые модели, источники скачивания, лицензионные условия и порядок обновления весов;
- требования к обработке сообщений: кто имеет доступ к серверу и журналам, сроки хранения, резервное копирование и согласования с участниками.

Характеристики сервера университета пока не подтверждены. В [выборе модели](MODEL-SELECTION.md) приведены планировочные оценки, а не подтверждённые требования. До пилота нужно проверить фактическую память, скорость и качество на обезличенных данных.

## Локальная проверка API и модели

Требуется Docker Engine с Compose plugin. Для облачной модели локально хранить веса не нужно. Передавать реальные сообщения студентов стороннему API можно только после согласования с организацией; до этого используйте синтетические или обезличенные данные.

1. Скопируйте `.env.backend.example` в `.env` и задайте уникальный длинный секрет:

   ```sh
   cp .env.backend.example .env
   openssl rand -hex 32
   ```

   Вставьте выведенный секрет в `ANALYSIS_API_TOKEN`, а API-ключ из `platform.deepseek.com` — в `DEEPSEEK_API_KEY`. Это разные ключи: первый проверяет доступ расширения к нашему backend, второй нужен backend для запросов DeepSeek. Не добавляйте `.env` в Git и не отправляйте секреты в переписке.

2. Соберите и запустите API:

   ```sh
   docker compose -f compose.backend.yaml --env-file .env up -d --build
   ```

3. Проверьте процесс API и готовность endpoint:

   ```sh
   docker compose -f compose.backend.yaml ps
   curl http://127.0.0.1:8787/healthz
   ```

   Health endpoint проверяет только доступность API, но не доступность провайдера или баланс. Для контрольного вызова используйте синтетическое сообщение и проверьте расход в кабинете DeepSeek.

4. Для остановки используйте `docker compose -f compose.backend.yaml --env-file .env down`.

Чтобы вместо облачного API использовать локальную Ollama, задайте в `.env` `ANALYSIS_PROVIDER=ollama` и `ANALYSIS_MODEL=qwen3.5:9b-q4_K_M`, затем запустите Compose с `--profile ollama` и скачайте модель. Для GPU администратор должен настроить совместимые драйвер и NVIDIA Container Toolkit, затем подтвердить работу замером. Образ Ollama в примере использует тег `latest`; перед эксплуатацией зафиксируйте проверенный тег или digest.

## Доступ из внутренней сети

API-контейнер требует `ANALYSIS_API_TOKEN` не короче 32 символов и принимает его в заголовке `Authorization: Bearer …`. Для DeepSeek backend отдельно использует `DEEPSEEK_API_KEY`; этот ключ нельзя помещать в расширение или отправлять клиентам. В Compose порт API опубликован только на `127.0.0.1` сервера, а порт Ollama `11434` наружу не опубликован. Разместите на том же сервере reverse proxy с TLS по [примеру nginx](../deployment/nginx-analysis.conf.example) и направьте HTTPS-запросы на `http://127.0.0.1:8787`; сохраняйте заголовок `Authorization` и путь `/v1/analyze`. Администратор должен подставить внутреннее DNS-имя и сертификат, затем ограничить входящий трафик по правилам организации. Не снимайте loopback-привязку контейнерного порта и не открывайте Ollama в сеть.

В установленном расширении откройте **Управление расширением → Параметры**. Введите HTTPS-адрес reverse proxy и значение `ANALYSIS_API_TOKEN`. При сохранении Chrome запросит разрешение только на указанный адрес. Адрес и ключ хранятся локально в профиле браузера пользователя; ключ не синхронизируется через Chrome Sync. Для локального Docker укажите `http://127.0.0.1:8787` и тот же `ANALYSIS_API_TOKEN` из `.env`.

До подключения реальных групп проверьте сертификат, сетевую доступность с клиентского компьютера, доступ только у предполагаемых пользователей и ротацию ключа. Ключ API является общей bearer-учётной записью без персональных ролей и отзыва отдельных пользователей; при пилоте ограничьте его распространение и согласуйте процедуру смены.

## Ошибки и диагностика

| Результат | Что проверить |
| --- | --- |
| `service_unavailable` | Разрешение Chrome на адрес, DNS, VPN/внутреннюю сеть, TLS-сертификат и reverse proxy. |
| `unauthorized` / HTTP 401 | Совпадает ли ключ в параметрах расширения и `ANALYSIS_API_TOKEN`; после смены секрета перезапустите API и обновите ключ в расширении. |
| `request_timeout` / `model_timeout` | Загружена ли модель, хватает ли памяти, нет ли очереди запросов; сначала попробуйте меньший пакет. |
| `model_provider_unavailable` | Исходящий HTTPS-доступ сервера, DNS и журналы backend. |
| `model_provider_http_error` | `DEEPSEEK_API_KEY`, баланс DeepSeek и имя модели. |
| `ollama_unavailable` | Состояние контейнера Ollama и значение `OLLAMA_URL`; в Compose оно должно быть `http://ollama:11434`. |
| `ollama_http_error` | Наличие точного тега модели (`docker compose ... exec ollama ollama list`) и сообщения журналов Ollama. |
| `invalid_model_json` / `invalid_model_response` | Версия и тег модели, доступная память, журналы сервиса; не записывайте текст сообщений или полный prompt/response в логи. |
| HTTP 413 `request_too_large` | Ограничение размера запроса; текущий API отклоняет тело больше 512 КБ. |

Сервис не журналирует тексты запросов и ответов. Для диагностики используйте `docker compose -f compose.backend.yaml logs --tail=100 analysis-api ollama`, состояние контейнеров и код ошибки. Не включайте дампы тел запросов в reverse proxy.

## Ограничения подготовки

Это воспроизводимый стенд для внутреннего пилота, а не готовое промышленное развертывание. Адрес сервера и правила доступа от университета пока не получены; нет пользовательской авторизации, отдельных ключей, ротации без перезапуска, мониторинга GPU, резервного копирования конфигурации и SLA. Перед передачей в эксплуатацию эти параметры должен подтвердить администратор организации.
