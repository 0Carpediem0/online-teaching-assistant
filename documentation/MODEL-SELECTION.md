# Выбор модели для анализа чата

## Краткое решение

Для первого локального пилота выбираем **Qwen3.5 9B Q4_K_M** (`qwen3.5:9b-q4_K_M`) через Ollama, развёрнутую на сервере вуза.

Это минимальный кандидат, который имеет смысл проверять на смысловом разборе русскоязычного учебного чата. Он должен классифицировать сообщения, выделять вопросы и технические проблемы, объединять похожие вопросы в общие формулировки и возвращать ссылки на исходные сообщения. Это **рабочая гипотеза для пилота, а не подтверждённая оценка качества**: модель ещё не проверена на размеченных сообщениях Телемоста.

Выбор предполагает, что сервер вуза доступен расширению по защищённому соединению и имеет GPU с достаточной памятью. Точных характеристик сервера пока нет, поэтому решение по железу предварительное.

Qwen3.5 заявляет широкую языковую поддержку, однако это не доказывает качество именно на русских вопросах студентов. Поэтому модель считается минимальным кандидатом для проверки, а не уже подтверждённо подходящим решением.

## Что должна делать модель

Модель получает только сообщения, впервые обнаруженные после старта занятия, без имени автора. У каждого сообщения есть идентификатор, номер версии и время, показанное Телемостом.

Для каждого сообщения модель возвращает:

- класс: `question`, `technical_issue`, `other` или `uncertain`;
- тему, если её можно определить;
- идентификатор версии исходного сообщения;
- оценку уверенности.

Для похожих вопросов модель создаёт `compiledQuestion` — краткую общую формулировку — и список `eventIds` исходных сообщений. Она не должна добавлять содержание, которого нет в исходных репликах. Неуверенные и неоднозначные сообщения следует оставлять отдельными, а не принудительно присоединять к теме.

Модель не считает статистику. Расширение считает число вопросов в пятиминутных интервалах по времени Телемоста и по классификациям модели. Так числа в интерфейсе получаются детерминированно, а модель отвечает за смысловую группировку.

Чтобы не вызывать модель отдельно на каждое короткое сообщение, для пилота рекомендуется собирать сообщения в пятиминутные пакеты. При закрытии интервала пакет замораживается и отправляется на анализ. Модель классифицирует сообщения и группирует похожие вопросы внутри пакета. В конце занятия можно выполнить дополнительное объединение уже готовых групп из разных интервалов; для него достаточно передать сводные формулировки и ссылки на исходные `eventIds`, а не повторно отправлять весь сырой чат.

## Почему этот вариант

### Почему не Dolphin, установленный на компьютере

В локальном Ollama найден `local-unfiltered:8b`. По метаданным это Dolphin 3.0 Llama 3.1 8B Abliterated в квантизации Q4_K_M, размером около 4,9 ГБ. В метаданных базовой модели указан английский язык. Вариант нацелен на снятие ограничений, но не на русский анализ учебного чата. Поэтому этот результат не является надёжной оценкой всех локальных моделей.

Также установлен `freehuntx/qwen3-coder:8b` — модель для задач по коду. Она не является подходящим кандидатом для классификации сообщений и сведения вопросов.

### Почему не 4B

Qwen3.5 4B компактнее, но наша задача требует учитывать смысл и контекст нескольких реплик, а не только распознавать простые ключевые слова. Для свёртывания похожих вопросов риск потери качества слишком велик. Модель 4B можно оставить только как технический резерв, если сервер не тянет 9B, но не как принятый вариант по умолчанию.

### Почему не 27B сразу

Qwen3.5 27B Q4_K_M занимает около 17 ГБ только в опубликованном виде весов. Ему понадобится заметно больше памяти во время работы. Пока спецификации сервера неизвестны, закладывать эту модель как обязательную нельзя. Если 9B плохо объединяет вопросы, а у сервера достаточно GPU-памяти, 27B будет первым кандидатом на сравнение для повышения качества.

## Предварительные требования к серверу

Опубликованный размер весов Qwen3.5 9B Q4_K_M — около **6,6 ГБ**. Это размер файла модели, а не полный объём необходимой видеопамяти: во время работы память расходуется также на контекст, KV-кэш, runtime и параллельные запросы.

Для первичного размещения следует ориентироваться на:

- GPU с **16 ГБ VRAM** как предпочтительную конфигурацию для одной загруженной модели и коротких запросов;
- **32 ГБ системной RAM**;
- не менее **20 ГБ свободного места** под модель, runtime и служебные файлы;
- короткий рабочий контекст, ориентировочно **8K токенов**, с обработкой небольшими пакетами;
- на первом этапе — последовательную обработку пакетов или низкую параллельность.

Это инженерная оценка для планирования, а не официальная гарантия производителя. При 12 ГБ VRAM модель может запуститься с ограниченным контекстом и одной задачей за раз; это нужно подтвердить на самом сервере. На CPU запуск тоже возможен, но подходящую задержку для занятия обещать нельзя. Если доступно только 8 ГБ VRAM, сначала нужно провести пробный запуск и замер; автоматический переход на 4B не считается решением по качеству.

## Развёртывание и конфиденциальность

Целевой контур:

```text
Расширение
  → защищённый API-сервис вуза
  → Ollama с Qwen3.5 9B на закрытом сервере вуза
  → проверенный JSON-ответ
  → панель преподавателя
```

Слово «локальная» здесь означает локальный для организации inference: сообщения передаются с компьютера преподавателя на сервер вуза, но не отправляются внешнему провайдеру модели. Пока API-сервис вуза не подтверждён, текущий прототип остаётся локальным только в смысле хранения событий в памяти вкладки.

Правила обработки:

- не отправлять имя автора;
- не отправлять DOM или HTML страницы;
- передавать только текст, время Телемоста, `eventId`, `revision` и необходимые идентификаторы пакета;
- передавать данные только после старта занятия;
- держать модельный API во внутренней сети и не открывать его напрямую в интернет;
- использовать TLS и авторизацию на API-сервисе; секреты не встраивать в код расширения;
- не писать тексты сообщений и ответы модели в журналы приложения;
- не сохранять сырой чат на сервере после обработки, если для выбранного сценария он не нужен;
- ограничить исходящие сетевые подключения сервера после загрузки модели, если это позволяет инфраструктура.

Локальное размещение уменьшает число сторон, получающих содержимое чата, но само по себе не гарантирует конфиденциальность. Нужно выяснить правила доступа администраторов, резервного копирования, сетевого журналирования и хранения данных на сервере вуза.

## Взаимодействие с моделью

Расширение и сервис обмениваются JSON по контракту из [схемы обработки данных](DATA-FLOW.md). В запросе фиксируются `analysisId`, `eventId` и `revision`. Перед передачей пакет замораживается: редактировать можно только сообщения, по которым анализ ещё не начался.

Для Ollama используется `POST /api/chat` с `stream: false` и параметром `format`, которому передаётся JSON Schema результата. Начальный режим — температура `0` для более воспроизводимой классификации. После ответа сервис:

1. разбирает JSON и валидирует его по схеме;
2. проверяет, что каждый `eventId` и `revision` соответствует отправленному пакету;
3. отклоняет неизвестные ссылки и недопустимые категории;
4. передаёт валидные результаты интерфейсу;
5. считает пятиминутные пики программно по времени Телемоста.

JSON Schema гарантирует форму ответа, но не истинность классификации. Смысловые ошибки выявляются оценкой на примерах.

Для воспроизводимости после выбора версии нужно зафиксировать точный тег и digest загруженных весов, версию Ollama, размер контекста, параметры генерации и ревизию промпта. Плавающий тег `latest` в целевом развёртывании не использовать.

Содержимое сообщений следует считать недоверенным пользовательским вводом. Инструкции внутри реплик студентов не должны менять задачу модели или её формат ответа.

## План проверки качества

Перед фиксацией модели как производственной нужно собрать небольшой обезличенный набор сообщений и вручную отметить:

- какие сообщения являются вопросами;
- какие сообщают о технических проблемах;
- какие вопросы семантически повторяют друг друга;
- допустимую сводную формулировку и связь с исходными репликами.

Сравнивать кандидатов нужно на одинаковом наборе, одинаковой JSON-схеме и одинаковых промптах. Минимальные метрики:

- precision/recall/F1 по классам сообщений;
- точность объединения похожих вопросов и доля ошибочно склеенных разных вопросов;
- доля сообщений, оставленных `uncertain`;
- доля валидных результатов, с корректными ссылками на исходные события;
- медианное и 95-процентильное время ответа;
- загрузка VRAM и RAM при предполагаемом числе одновременных занятий.

Временные пики проверяются отдельно: расширение должно корректно разнести сообщения по пятиминутным корзинам, а модель — правильно определить, какие из них являются вопросами. Нельзя оценивать работу только по впечатлению от нескольких демонстрационных запросов.

## Когда пересмотреть выбор

- Если Qwen3.5 9B путает вопросы и утверждения или плохо объединяет переформулировки — сравнить с Qwen3.5 27B Q4_K_M на том же наборе.
- Если 9B не помещается или не выдерживает требуемую параллельность — уточнить фактические GPU/RAM и замерить оптимизацию контекста; только затем решать, допустима ли меньшая модель.
- Если модель не достигает минимальной точности даже после настройки промпта — не выдавать сомнительную сводку как факт; показывать исходные сообщения и статус «требует проверки» либо пересмотреть модельный контур.
- Если вуз не предоставляет закрытый сервер с подходящими ресурсами и условиями доступа, локальный организационный inference пока не подтверждён. Облачный API потребует отдельного решения, потому что текст сообщений покинет инфраструктуру вуза.
